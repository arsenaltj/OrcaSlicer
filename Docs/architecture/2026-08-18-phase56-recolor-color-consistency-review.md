# 阶段 56 架构复核：局部改色颜色一致性

## 结论

本次修复只调整 3D 生成页的选区预览和 UI 状态同步，没有改变标准 OBJ 顶点色 RGB 顺序，也没有进入 Orca 的切片、3MF、打印配置或耗材配置。阶段 55 建立的“独立网格编辑器—GUI 预览—现有 OBJ 导入”边界保持不变。

## 根因与修复边界

- `VertexColorRegionEditor` 原有写出路径始终按标准 RGB 输出，Orca `load_obj` 也按相同顺序读取，不需要也不允许增加 BGR 特例。
- 视觉误判来自 `ModelPreview3D` 的固定不透明青色选区层：原绿色区域被覆盖时看起来像蓝色。选区层现在使用当前目标耗材色，目标下拉变化后立即刷新。
- 模型成功重载会清空编辑器内部选区；本次补上统一的零选区通知，使三角面计数、应用按钮和实际编辑器状态保持一致。
- UI 仍只传入预览颜色和显示状态；实际 OBJ 改色继续由独立 `VertexColorRegionEditor` 完成。

## 兼容性

- 未改变 OBJ 文件格式、颜色范围、Alpha 处理、对象/分组、材质、UV、法线或三角面拓扑。
- 未修改现有历史模型元数据结构，旧的局部改色 OBJ 可以继续加载。
- 未修改 Orca 核心模型载入逻辑；新增往返测试直接复用 Orca 的 `load_obj`，用于约束红、绿、蓝三通道顺序。
- 功能只在 3D 生成页的可编辑 OBJ 预览中生效，普通 Orca 导入、准备与切片流程不受影响。

## 验证与剩余风险

- 正式 Windows GUI 已验证绿色选区预览、应用、重新加载和选区清零完整闭环；最终 OBJ 中绿色为 `0 1 0`，不是 `0 0 1`。
- Windows Release 的 GUI 库和完整程序均已构建并部署。
- 当前主构建关闭 Catch2 测试目标，因此新增红/绿/蓝往返测试只完成源码审查，尚未在这个 build 目录运行；应由后续启用测试的 CI 配置执行。
- 选区预览与目标色完全相同时可能降低边界可见性。当前用选择计数和应用按钮提供状态反馈；若后续需要更强边界提示，应增加轮廓线，而不是再次使用会误导最终颜色的固定覆盖色。

## 1. 目标、事实和边界

目标是消除已有中央内容在刷新中消失再恢复的现象，并使上传及首次模型显示连续衔接。沿用当前Figma布局、图片、字体、颜色、中文文案、进度算法、动画效果、完成双按钮和成功提示。

| 场景 | 已取得的事实 | 本方案处理 |
| --- | --- | --- |
| 智能页启动 | 引导插画首次出现后闪烁3次，每次约33ms，标题仍在 | CF-01背景保护、CF-02按变化刷新 |
| 智能上传 | 两轮中央切换空白约0.517／0.417秒；加载后未见反复消失 | CF-02减少重复工作、CF-03连续交接；不把“多次反复”写成已完整复现 |
| 智能3D生成 | 规律空白约1.55秒；分析窗口49次空白与状态提交高度对应，模型显示后稳定 | CF-02为主要修复，CF-01及CF-04配合 |
| 高级3D生成 | 本轮完整录像未见周期整块空白；首次模型显示前取景区空白约0.75秒 | 覆盖共用展示保护和CF-04；不推定高级拥有智能整页刷新链，不宣称其周期问题已定位或修复 |

三条原底线继续有效：智能业务正常、高级业务正常、工作台编辑→导入切片→切片→打印原流程正常。本方案不改变提交／计费、供应商、任务参数、轮询周期、智能2D准备→3D规则、高级四图与确认、停止／恢复、历史格式、工作台编辑资产或下游规则；不进行全局UI框架重构。

## 2. 状态归属与依赖

- 智能输入、任务、资格及恢复仍归既有Host／原流程；高级四图、确认及任务仍归Session／Host／TaskFlow。
- Shell只适配展示和原命令；共用InlineModelGenerationView只拥有本地准备、显示代次及有效首帧状态。
- 新增的“哪些显示属性变化”“某个缩略图是否需要重算”等只属于可丢弃的展示缓存，不建立第二份任务状态，也不作为提交资格依据。
- 沿用既有RefreshScheduler、TaskRunner／TaskScope和首帧观察能力；本补丁不修改其通用实现，不给内核或供应商增加GUI反向依赖。

### 2.1 展示更新的开发约束

一次有效任务快照的处理顺序为：原身份及版本检查 → 原状态与动作资格更新 → 生成新的展示投影 → 比较受影响显示属性 → 提交必要的位图／显隐／尺寸变化 → 局部重绘。比较结果只能减少控件写入，不能取消业务快照消费。

| 展示缓存／标记 | 内容与失效条件 | 不承担的职责 |
| --- | --- | --- |
| 中央内容类型／显隐 | 引导、图片、生成反馈、模型预览，以及当前各控件可见性 | 不决定任务创建、停止、恢复或来源归属 |
| 已安装图片位图资格 | 已成功解码内容的代次、目标像素尺寸、DPI及已有裁切／圆角规则 | 不以缓存判断输入合法性或可生成资格，不新增文件摘要计算 |
| 已应用控件属性 | 反馈矩形、实际文案、显隐与动作可用性 | 不阻止阶段／终态或新动作资格更新 |
| 首帧交接标记 | 复用当前来源、任务、资产和呈现代次绑定；尺寸／DPI改变时重验 | 不新增Ready业务状态，不提前发完成提示 |

直接复用现有字段和控件已安装位图；必要新增字段限定于本地显示缓存。相同路径重新选择了不同内容时，使用成功解码／内容更新代次使位图失效；页面重显、缓存缺失或恢复输入也必须能从原状态重新构造画面。

### 2.2 交接规则

| 交接 | 撤下旧画面的条件 | 失败／过期处理 |
| --- | --- | --- |
| 引导／原图片 → 新上传图片 | 新图片完成原校验，显示位图可安装，提交本次必要控件变化 | 原业务按现有规则处理失败／取消；旧回调不能装回过期图片 |
| 生成反馈 → 模型预览 | GL按最终尺寸绘制，原观察器确认当前资产有效首帧 | 继续原失败／超时提示；不放宽首帧资格，不永久覆盖GL |
| 隐藏 → 恢复 | 可见性恢复后应用保留的dirty及最新展示属性 | 不恢复旧任务或旧尺寸帧，不重建付费请求 |

## 3. CF-01：补齐中央自绘背景保护

主要位置：`RedesignFlowGuide.hpp`的FlowGuideCanvas、`InlineModelGenerationView.cpp`的GenerationFeedback。

1. 两个控件继续使用现有wxAutoBufferedPaintDC，在构造时启用已有`paint_owns_background()`。
2. 保证各自正常paint在缓冲区内完整绘制背景和内容，再一次提交，避免背景擦除先独立填出纯色帧。
3. 普通内容更新采用`Refresh(false)`；不能仅机械替换所有Refresh，真实尺寸／显隐变化仍需正确重画暴露区域。
4. 不更改RedesignPaintPanel的全局默认值、恢复subclass、GL窗口策略或其他控件。ImagePreview已有的保护保留。

预期结果：启动引导和生成反馈的正常更新不再因独立擦底丢失内容。风险主要是初次显示、缩放及窗口恢复出现未重画区域，因此CF-01必须与恢复／尺寸场景一起验收；不以一行opt-in等同所有闪烁均已解决。

## 4. CF-02：智能进度只更新需要变化的展示

主要位置：`RedesignShell.cpp/.hpp`的`apply_model_generation_state`、`update_image_state`、`update_preview_bitmap`；必要的显隐适配位于`RedesignCreationModel.cpp`。共用控件的布局调整限定在`InlineModelGenerationView.cpp`。

### 4.1 业务状态始终处理，绘制按变化执行

不能在`apply_model_generation_state`开头以“仅进度变化”为由整体提前返回。每份有效快照仍走原身份／版本检查，更新原任务状态、动作资格、停止恢复、输入锁及历史通知。

仅对UI写入作以下区分：

| 实际变化 | 展示处理 |
| --- | --- |
| 进度、耗时、状态文字 | 更新当前等待控件并请求局部重绘；不重算输入图片，不重排中央页 |
| 输入图片／设计图内容变化 | 重建对应位图，再更新相关图片控件 |
| 上传Empty／Loading／Ready／Failed变化 | 更新上传槽的实际变化；中央是否切换按CF-03控制 |
| 引导／图片／生成反馈／3D预览显隐变化 | 提交一次必要布局和局部重绘 |
| 窗口大小、DPI、右栏宽度改变 | 重算受影响的尺寸和图像缓存，沿原调度器合并 |
| 阶段、成功／失败／停止或动作资格变化 | 立即应用相应显示和动作；不因刷新合并丢失终态 |

### 4.2 消除重复擦底、缩略图与布局

1. 去掉“每份状态快照无条件调用输入页全量更新”的耦合，改为比较相关展示属性后调用。仍覆盖恢复输入、清除输入、切图、旧单图兼容及返回创作等既有调用者。
2. 生成反馈正在占用中央区域时，不为隐藏的源图／设计图反复调用`rounded_thumbnail`、SetBitmap及多次Layout；恢复图片展示时按最新输入补齐。
3. 缩略图按图片内容代次、目标像素尺寸、DPI和现有裁切／圆角规则失效。不能只用路径或文件时间戳判断，防止同路径换图、恢复旧任务或DPI变化显示旧位图。
4. 中央父容器的重画只用于真实结构变化，移除进度路径的默认擦底和子树递归刷新。局部更新沿现有RefreshScheduler合并，不新建整页定时器。
5. 共用反馈的SetSize仅在矩形改变时执行；Raise仅在显隐／层级切换确有需要时执行。42ms动画只绘制自身，既有可见性暂停、计时连续性及隐藏dirty恢复保持。
6. 不改造风格列表或左／右侧栏的独立渲染系统；若其现有刷新仍间接触发中央重绘，只收紧本次状态提交中的相应调用条件，不顺带重构其他交互。

预期结果：智能约1.5秒一次的状态更新仍正常发生，但不再让整块中央内容先擦空。主要风险是过度省略更新，因此以输入恢复、终态、显隐、缩放和旧调用者回归约束缓存及dirty条件。

## 5. CF-03：上传采用准备完成后连续交接

主要位置：`RedesignShell.cpp`的`accept_image`及图片展示更新；必要局部缓存字段限于`RedesignShell.hpp`。

1. 用户选图后，上传槽继续按原规则显示Loading并限制重复操作；中央保留当前有效的引导或原图片，直到新图片具备绘制条件。
2. 解码、尺寸验证和对应显示位图准备成功后，执行原输入更新／同步流程，并合并本轮中央显隐、位图及必要布局，避免先隐藏旧画面、后等待新内容。
3. 界面在Loading时保留的只是已显示像素，不代表原图仍是待提交输入；生成资格继续读取原Host和输入同步结果。同步失败或不可生成时保留原禁用规则。
4. 文件取消、校验失败、替换失败按原规则保留旧输入／旧成果或显示失败，不把失败的候选图当成新输入，不因界面保留旧像素绕过原保护。
5. 保留`m_image_request_generation`等既有过期结果保护；清除输入、切来源、退出或开始后续请求后，旧回调不能重新覆盖当前画面。
6. 本轮先消除重复布局／缩略图和提前清空；不迁移整条上传／HTTP同步到新线程，不新增线程池。短时布局冻结如确有需要，只覆盖同步控件提交，不跨CallAfter、HTTP、异步等待或文件处理。

保留原输入更新／同步顺序、错误处理及提交门禁。保留画面优先复用当前控件已安装位图或已显示引导，不再复制一份可写业务输入；不以“画面还显示旧图”为理由允许用户提交加载中的候选图。

预期结果：原引导／图片直接切换成新图片，正常上传过渡中没有整块纯背景。总加载耗时不作为本补丁的固定性能承诺；若连续显示修复后仍存在独立卡顿，记录为独立问题，不扩大本补丁。

## 6. CF-04：生成反馈连续交接到有效模型首帧

主要位置：`InlineModelGenerationView.cpp`的layout、render、install和现有首帧回调。两种模式共同受益。

当前进入AwaitingFirstFrame时，GL预览尚未确认有效首帧，全幅等待反馈已缩到底部。拟将“准备GL显示”和“撤下中央等待画面”分开：

1. 下载、CPU解析／准备期间继续显示原全幅反馈。
2. AwaitingFirstFrame仍按最终尺寸挂载并显示GL预览，注册原`observe_presentation_frame`；全幅反馈作为短暂呈现保护保留到该回调确认。不能把GL窗口一直Hide后再等待可见首帧，否则会形成循环等待。
3. 首选在现有共同父容器内调整反馈／预览的层级和撤下时机，保持GL最终尺寸；仅在这一阶段执行必要的一次呈现提交，普通进度不调用同步Update。
4. 实窗确认该覆盖不会阻止GL收到绘制或使帧回调误判可见；若原生GL子窗口无法稳定配合，限定在本地交接适配中复用已有的保留源画面／首帧提交方式。不能为此改全局GL渲染器、复制工作台路由事务或增加新的模态窗口。该平台细节必须在本项验证中解决，不能仅以Raise调用完成宣称通过。
5. 只有当前来源、任务、模型路径／摘要、呈现代次以及尺寸／DPI相符的有效首帧到达，才撤下保护，沿原规则进入Ready，显示双按钮和一次完成提示。
6. 首帧失败／超时继续显示原失败说明及重新加载入口；切页、最小化、换任务或关闭使旧回调失效。沿用原deadline及隐藏暂停规则，不放宽ready条件或改变成功提示触发规则。

预期结果：中央持续显示原等待反馈，随后直接出现真实模型；修复所录到的约0.75秒过渡空白，同时避免模型未显示就提前解锁“进入工作台”。这是本补丁风险最高的一项，应单独验证GL首帧、显隐、尺寸变化及超时后再合入完整结果。

实施沿同一现有分支、同一checkout增量构建，按以下开发步骤推进。表中为未来实施步骤，不表示现在已经执行。

| D2 上传交接 | 实施CF-03，候选准备期间保留已显示画面，成功后提交必要控件变化 | FC-02～05；原失败／取消／输入同步与过期结果保护保持，正常成功切换无纯背景 |

| D4 构建与回归 | Windows增量编译、必要定向自动回归、完整匹配运行树、主窗口录屏及消费者验证 | 按配套20条分别记录结果和未覆盖分支；真实等待／打印条件不足时保留未验证，不冒充全通过 |
| D5 交付 | 差异复核、同步必要维护文档、更新原主计划／短状态，交付EXE及证据路径 | 提供代码／产物身份、构建和测试结论、已解决与未验证项；不自动commit／push／发布 |

构建期间不修改源码。CF-04的GL相容性是开发内的技术验证点，按限定局部方案解决；若必须修改共享渲染器或跨出既定边界，再说明必要范围，不以技术验证点要求用户逐步审批。

### 7.1 风险与控制

| 风险 | 控制措施 | 对应用例 |
| --- | --- | --- |
| 为减少刷新而丢掉终态／动作更新 | 先消费原快照，只对控件写入去重；阶段及终态即时处理 | FC-06／13／14／16／17 |
